## What Invariant is

A code factory that turns GitHub issues into merged pull requests. The code in each pull request is proved or tested against formal statements that people have ratified, or, for plumbing, against the tests of a plan they ratified. `D-0000` `D-0002` `D-0024` `D-0105`

## Principles

- **Ordinary code stays natural, and the critical parts are proved.** @gitdek's direction for Invariant: "Invariant should let developers mix idiomatic Go and Python with formal verification without forcing entire applications into a restricted dialect. Keep ordinary code natural, prove critical components, and check how the surrounding code interacts with them. Support incremental adoption, clearly distinguishing proved guarantees from tested behavior." A component is proved as a standalone core in the prover's own style, in a project of its own, with the code around it taking the core's step first by hand, or, in an existing Python application, as a function a check selects, proved in place in its real module beside conformance on the same function (#359) or declared calls recorded on accepted and refused explored attempts (#793). The work toward proving components in place includes Go and Python source inventories, validated selections, assumptions and inert invocation declarations with exact input provenance, and APIs for independently attributing supplied proof, unverified assumption, conformance, runtime and trusted contracts' backing-test records. Conformance separately qualifies checked transitions, exhaustive states and tried steps; runtime separately qualifies actual tests and assertions; optional actual proof provenance remains compatible with old callers. #296 completes the supplied evidence and provenance receipts in #244's foundation for the narrowed step 1 of #210; component dashboard views remain later work. #210's plan was then narrowed to the path ask3d needs, and #294 delivered it: it checks unchanged Python against a model, backs trusted dependency contracts with tests and proves selected Python functions in place, each in the gate, while #210's Go steps and the checks on callers and on evidence regressions wait until ask3d shows they're needed. TypeScript discovery is outside this ordinary Go and Python scope. `D-0152` `D-0158` `D-0163` `D-0122` `D-0168` `D-0169` `D-0170` `D-0171` `D-0172` `D-0175` `D-0177` `D-0198` `D-0213` `D-0260` `D-0416`
- **People decide what must be true, and the factory proves that it is.** The factory drafts formal statements, and a person ratifies them before the factory builds against them. Ratified statements are pinned by hash, and the factory cannot change them. Changing one takes a new decision. `D-0002`
- **The factory doesn't guess.** When it can't formalize an issue without choosing between interpretations, it posts the fork on the issue as a decision request and does not proceed on that fork. `D-0002`
- **Proofs where the rules are, tests where the plumbing is, and people make every decision that matters.** People decide every requirement, fork and statement, and a coding agent's two-way calls while it builds stand only until the owner reverses them. Invariant proves the rules that make it trustworthy, as projects under `factory/`. Coding agents build everything else, tested by CI. `D-0022` `D-0048` `D-0254`
- **A small trusted base.** A bug outside the gate, CI and the merge decision can stop a merge, but it can't produce a bad one, because the gate checks everything the factory makes. Changes to the trusted base land by pull request, and @gitdek merges them once CI passes. `plumbing.TrustedBase` lists what only a person merges. `D-0048` `D-0109`
- **Checks can't be quietly weakened.** The gate writes TLC's config itself from what was ratified. Reachability witnesses show the invariants don't hold only because the model does nothing. Known bugs show the invariants are strong enough to catch real mistakes. `D-0011` `D-0013` `D-0017`

## What gets ratified

- Each project's `.invariant/ratified.lock` records five things, and two more when something must eventually happen, beside who ratified them and where. `D-0011` `D-0013` `D-0026` `D-0034` `D-0071`
  - The spec, `Init /\ [][Next]_vars`.
  - The invariants.
  - The bounds TLC checks them within.
  - The reachability witnesses.
  - The known bugs, as TLA+ actions the invariants, or a property, must catch.
  - The properties: temporal formulas every behavior must satisfy, such as every command eventually being answered.
  - The fairness they assume: `WF_vars(A)` or `SF_vars(A)`, one condition each, optionally for each `x` in a set, about the system's own steps. The spec never states fairness itself.
- Each pin covers a statement and every definition it depends on, stopping at the factory's `Init` and `Next`. So a fairness statement pins the action it names, and the model must keep that action a part of `Next`. `D-0026` `D-0071`
  - The gate takes a pin's text by [reading the model the way TLC's parser does](docs/gate.md#how-the-gate-reads-a-model), and refuses a model it can't read exactly, with the line (#812). It reads strings and nested comments as SANY does, and a module only from its header, which comes first, to its closing line. Every line at the left margin starts a definition, a declaration or a separator, and no unit may hold the start of another: a second `==` outside a `LET`, or a word that starts a unit. `INSTANCE`, `LOCAL`, theorems, definitions of operator symbols, a name defined twice, a character outside ASCII in code and a record field named `LET` or `IN` are refused. A model extends only `Naturals`, `Integers`, `Sequences`, `FiniteSets`, `Bags`, `TLC` and modules beside it, whose definitions join a pin's closure, and none of its modules has the name of one TLC ships. What a pin covers may use `\div` only where the model extends `Integers`, since TLC rounds it differently without. The same reading names the steps of `Next` and the action a fairness statement holds. A test holds each reading against the pinned TLC. No ratified pin changed. A pin doesn't cover a statement's layout yet (#814). `D-0423`
- The factory owns the model (`Init`, the actions and `Next`), the implementation and its contracts. Each contract restates one TLA+ action. `D-0011` `D-0026` `D-0031`
- A bound is one name and one value: a number, a model value, a string, or a set or tuple of them, on one line. The gate writes each into TLC's config as a constant, and TLC reads that file a token at a time, so a value that held a second value or a line end would add a directive of its own, such as a constraint that prunes the states TLC checks. A lock or a draft with such a bound is refused (#826). `D-0017` `D-0428`
- A person pins a lock's statements with `invariant pin`. For a lock ratified by hand, it also prints the lock's proposal, and the `invariant decisions ratify` line that names it while no person's ratify line does. `D-0017` `D-0208`
- A project's manifest may also select ratified invariants in `tlaps`, for TLAPS to prove at every size. Selecting one claims evidence and changes no statement, so it isn't in the lock, and the proof itself, at `.invariant/proofs/<Inv>.tla`, is untrusted, like the code. `D-0229` `D-0231`
