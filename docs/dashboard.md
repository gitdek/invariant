# The dashboard

The [live dashboard](https://invariant.puglisij.com/) shows the factory at work. `invariant dashboard -repo OWNER/NAME` serves it on http://127.0.0.1:8484, beside the factory [the README](../README.md#use-it-on-your-repository) sets up. This page says what its cards show and keep, and what the private `/act` page adds.

## Repository views

The page shows every repository `-repo` names, Invariant's own first. **Show** chooses one of them or everything, and each choice is a link to its view's address: `/?repo=ask3d`, with the repository's short name, or owner/name when two repositories share it ([#773](https://github.com/gitdek/invariant/issues/773), [D-0409](../decisions/journal/D-0409.jsonl)). The page opens on the repository its address names, or on the last choice when the address names none, and keeps the address on the view it shows, so a view can be bookmarked and shared, and back and forward move between views. A repository the page doesn't show opens Everything.

In a repository's view, every part shows only that repository: its headline and the page's title, what needs a person, its running or last finished steps, its numbers, its projects and their state charts, its issues, its activity and its decisions. Another repository's decisions come from its own journal, `decisions/journal`, read at its branch's head, and its decisions tile counts its own calls; a repository without a journal says it has none. The road and who builds what describe Invariant itself, so they show only in Invariant's view and in Everything. Another repository's commits aren't read, only its branch's ref.

Each repository says what it has established in plain words, never as a count of projects ([#775](https://github.com/gitdek/invariant/issues/775), [D-0410](../decisions/journal/D-0410.jsonl)). Show's choices say it briefly, as `nothing proved yet · 1 tested`, and a repository's line and its star in the fleet in full, as `231 functions proved · 14 models checked · 131 changes tested`. Before the numbers, each repository in view has a row with three levels. **Proved** counts the functions Gobra and Nagini proved. **Model-checked** counts the models TLC checked, with the states it explored. **Tested** counts the changes merged under a ratified plan, with the acceptance tests those plans pinned. A level with nothing in it says so. Tested changes are the plans on the repository's branch, in `.invariant/plans`, read in one query at its head, and only a ratified plan counts.

## Reader evidence

Each modeled project's checked reader chart, from CI's receipt archive, links to a script-free evidence page, which links the standalone `image/svg+xml` image. The shared native Go renderer draws the complete chart and report: literal labels, verbatim locked rules, unavailable model actions, all hidden occurrences and view-rule IDs, separately defined counts, checked bounds and source/tool provenance. The image works without scripts or a browser renderer. Its page identifies the repository, full project path and receipt commit, keeps the locked wording readable as text, and includes the complete reader record. Neither adds a proof claim or changes the receipt's verdict or code assurance.

Every evidence page, a merged project's, a proposal's and an option preview's, wears the dashboard's look ([#786](https://github.com/gitdek/invariant/issues/786), [D-0415](../decisions/journal/D-0415.jsonl)): its dark palette, Space Grotesk and JetBrains Mono, chips for the language, what the code earned and the result, and a link back to its repository's view. A merged project's page links to GitHub at its receipt commit: the issue and the ratifying comment for a factory project, or the decision for one ratified by hand, the model, the project's folder, the code it checks, the commit and the repository. The checked code is linked only where the commit's tree places it as the gate does, beside the nearest `package-lock.json` above a TypeScript project or in the one folder above a Python project that holds every named source; otherwise it's named without a link. A proposal's or an option's page links its issue, and neither offers a command: ratifying stays on the cards. The rules read as cards grouped by what they promise, what must always hold, what can happen and the bugs the check must catch, each with what the receipt found: held in every checked state, reached in so many steps, caught. The pages stay script-free and sandboxed; their policy adds only the dashboard's fonts, styles from `fonts.googleapis.com` and font files from `fonts.gstatic.com`. A merged project's evidence keeps the identity and image URLs #723 pinned, and its page's link carries the page's own hash as a query, `?h=`, so a redesign reaches readers at once rather than from a cached copy.

The page shows projects as one row per model: projects whose models are identical share it, with the model's states, statements and bugs caught, who ratified it, and a chip for each implementation, its language, how it's checked, its code evidence and whether it passed, linking its own evidence page. Each row starts with a tile of the same size. A checked chart's tile frames the top of its [poster](statecharts.md#posters), drawn from the same checked record: animated, or still for readers who prefer reduced motion. When a mouse rests on the tile, or it has keyboard focus, the poster shows whole beside it, and clicking it opens the evidence page; on touch a tap opens the page. A model with no reader chart says why in its tile, with its checked state count, and the tile opens its evidence page. No raw graph stands in for a reader chart: **Raw state graph detail** stays a separately labeled view. The evidence page links the complete evidence image with the full report; the dashboard links no standalone image. The table view lists one line per project. [D-0367](../decisions/journal/D-0367.jsonl) records this layout, refining D-0364. A poster's bytes join its page's immutable identity, so a renderer change publishes new URLs.

The loader reads the manifest, model, every sibling TLA+ include, saved view and lock at the receipt commit, never a newer branch tip. It checks source hashes, reader and verification fingerprints, statement pins, bounds, completed model counts and tools against the report. Archived `reader.json` must equal the receipt's original reader record. Archived `reader.svg` must equal the shared renderer's output, with comparison-only presentation differences handled separately below. The server serves freshly rendered output, never arbitrary SVG from an archive. Ambiguous project basenames in the archive cannot supply reader charts for different full project paths.

Rows and evidence pages distinguish **no saved reader view**, legacy receipts, missing artifacts, snapshot mismatches, inconsistent companions and the receipt's generation-failure code. A project omitted from a partial receipt archive keeps its chip and missing-report explanation, without a verification verdict, results or claimed provenance. Charts include **500 reachable concrete states**; a checked `too_large` record explains the actual count, the 500-state capacity and the bounds, without drawing a partial chart. A missing view remains a missing-view explanation even for a large model. The 20-arrow target is advice. Plumbing cards have no reader presentation. Public reader responses include no private action data and cannot open `/act`.

Reader URLs and ETags bind the repository and full project path, receipt commit, exact reader inputs, lock, full receipt and displayed contents, SVG bytes and presentation format. The disk cache retains structured evidence and archive companions. Restart validates them again, renders with the current renderer and checks the resulting identity against the saved card; incompatible or damaged entries become visible diagnostics, never dangling chart cards. Each project's evidence is restored independently for the next refresh. If any project evidence is damaged, the saved whole-page snapshot is discarded until a refresh can recompute its totals; a failed refresh retains the healthy project sources and the damaged project's diagnostic. If the archive is absent or expired and no previous evidence exists, discovered modeled projects get missing-artifact cards and pages without verification results. Existing evidence remains visible when a newer archive is unavailable. Missing archives and damaged caches retry even when the gate run has not changed, including after restart. Entries from repositories outside the configured set are not served. These immutable reader URLs are independent of the raw graph cache.

**Raw state graph detail** remains a separately labeled view with its existing exploration/edge coverage and traces. It may compact graph display data; neither reader charts nor claims about unavailable actions are reconstructed from `Graph.Compact`. The [example inventory and validation command](statecharts.md#example-inventory) cover all ten examples and all nine qualifying siblings.

A proposal's chart, and each option preview's, is drawn as the same poster a merged project's page uses, wherever a person reads it ([#784](https://github.com/gitdek/invariant/issues/784), [D-0414](../decisions/journal/D-0414.jsonl)): its page shows the animated poster, with its still twin for reduced motion, a proposal's page lists the rules a person would ratify and the bounds, and its card shows the poster in place of the complete evidence image, which stays one link away. Modeled proposal cards on the public page and `/act` retain the checked proposal and its reader presentation, with immutable evidence pages and native SVG. [Proposal comparisons](statecharts.md#proposal-comparisons) show the complete candidate against its named captured baseline, distinct added and removed state/arrow annotations, dashed removals, hidden changes and a legend. Exact model/include/view/lock identities, both bounds, view and model-source qualifications and changed-scope notes accompany the chart. Equal charts do not establish behavioral equivalence.

Receipt evidence pages and companions retain that same proposal comparison alongside the freshly checked final model. Different final source identities are labeled explicitly. Under [#723's ratified plan](../.invariant/plans/issue-723.json), the loader uses verification's validation and printable diagnostic wording for `.invariant/comparison.json` at the receipt commit, even when the receipt omits comparison evidence. Binding is symmetric: both must agree on absence, the complete valid comparison, or the complete diagnostic, including its code, message and source. Candidate rules and bounds must match the captured lock; separately synthesized final model/include/view sources need not equal the proposal sources. An absent file differs from an empty or damaged file.

A comparison-only failure removes the comparison presentation and adds literal `comparison_evidence` text beside the affected implementation on public and `/act` rows and table entries, its evidence page and its final native chart. The complete independently valid final chart, report and animated/still posters survive. Final `too_large` and unavailable outcomes retain their specific explanation and counts without claiming a chart. Every final source, fingerprint, pin, bound, tool, count, chart-consistency and companion check still runs against the original retained receipt. Only comparison presentation differences in the native SVG panels are tolerated: the complete final drawing and report must match the shared renderer, not just embedded metadata. Arbitrary SVG and unrelated final damage cannot supply fallback. Rendering neither mutates nor reseals reports, and changes no verdict, assurance, verification fingerprint, proposal hash or lock.

Immutable URLs and ETags bind captured comparison bytes (including empty-file presence), diagnostics and rendered contents alongside the final sources and posters; unchanged evidence without a comparison keeps its existing identity. A legitimate comparison diagnostic survives restart, but corrupting its cached evidence still invokes D-0353's whole-snapshot refusal, archive retry and authoritative recovery. Proposal cache restoration remains independent: damaged proposal comparisons lose their image while healthy proposal and option siblings survive. Rechecking the captured baseline and candidate repairs proposal evidence; verification republishes receipt companions using the original project provenance. [D-0391](../decisions/journal/D-0391.jsonl) records #723's refinement of D-0351, D-0353, D-0362 and D-0364. CI's integration shards run the [pinned-TLC coverage](statecharts.md#proposal-comparisons) on every plumbing pull request ([D-0392](../decisions/journal/D-0392.jsonl)).

This presentation implements [#631's ratified plan](../.invariant/plans/issue-631.json), on [D-0343](../decisions/journal/D-0343.jsonl), [D-0347](../decisions/journal/D-0347.jsonl), [D-0349](../decisions/journal/D-0349.jsonl) and [D-0351](../decisions/journal/D-0351.jsonl). [D-0353](../decisions/journal/D-0353.jsonl) records the presentation and cache policy.

## Modeled decisions

The modeled decision view shows all alternatives together, each with its exact option words, checked chart or explicit size/repair diagnostic, and an immutable link to a script-free evidence page. Each choice retains the complete [preview snapshot](statecharts.md#modeled-alternatives) and its reader presentation in the state JSON. Pages show candidate rules, prior choices, checked bounds, full source/receipt/reader data and pinned tool provenance. They identify the repository, issue, fork and option and label every alternative unratified and model-only; no preview offers ratification or claims code assurance.

Preview cache identities bind repository, issue, containing fork and option IDs and words, exact model/includes/view, effective prior choices, diagnostics, receipts, tools, presentation format and rendered contents. ETags and immutable reader URLs change with any of those inputs. The server renders the checked structure with the shared Go renderer and never serves agent-supplied SVG.

Proposal comparisons and option previews share their cache lifecycle under [#730's ratified plan](../.invariant/plans/issue-730.json). Lookup retains the complete detached input record, keyed by evidence kind and current validation/rendering contract: all repository, issue, option, wording, source, choice, reader, comparison, receipt and diagnostic contents participate. An identical record shares one typed validation/render pass and successful atomic evidence save, including concurrent requests. Changed inputs miss even when statement hashes or reader fingerprints remain equal. Failed persistence keeps the validated page reusable and retries the save on the next lookup. Published identities still bind evidence and rendered bytes; the native script-free presentation, URLs and ETags remain unchanged under the same format.

Healthy restoration validates each saved record against its snapshot card, builds once and installs that exact presentation without rewriting the evidence file, then primes the same input lookup. An existing memory hit cannot bypass the saved-record or card checks. Isolated damage and obsolete-format diagnostics are saved with the restored snapshot, so the next restart reuses them. After successful snapshot replacement or restart restoration, the server removes unreachable proposal and preview pages, input lookups and evidence files. Publication coordinates builds and HTTP readers; every live repository, sibling and receipt reference remains available, including references retained beneath the private page's posted-command overlay. A delayed candidate is reinstalled before publication if another replacement retired it. Failed snapshot replacement leaves the current snapshot and its pages intact; receipt rejection runs no proposal cleanup. These rules refine [D-0353](../decisions/journal/D-0353.jsonl), [D-0355](../decisions/journal/D-0355.jsonl), [D-0362](../decisions/journal/D-0362.jsonl) and [D-0368](../decisions/journal/D-0368.jsonl), preserving receipt archive retry, source-snapshot trust and factory marker-author checks. [D-0394](../decisions/journal/D-0394.jsonl) records the cache refinement.

Restart restores and revalidates each option separately from project receipts. A swapped snapshot, changed source, missing cache record or corrupted option gets its own diagnostic page and no image. Healthy siblings retain their evidence and stable conditional responses, including through another restart. Partial answers hide only the answered questions and keep the remaining snapshots' original choice context until another draft is checked. This separate option recovery preserves the existing project policy: damaged project evidence discards the saved whole-page snapshot until a refresh can recompute totals. Plumbing, PRD and authenticated D-0328 step-fit questions have no charts.

This behavior implements [#639's ratified plan](../.invariant/plans/issue-639.json) on D-0002, D-0307, D-0328, D-0345, D-0347, D-0351 and D-0353. D-0355 records the option-preview and cache policy, and the merger runs the [pinned-TLC integration](statecharts.md#modeled-alternatives) when Docker is unavailable to the builder.

## Restarts

A restart serves the last run's snapshot at once, while it reads GitHub again, unless its cached reader evidence is damaged or obsolete, as after a change to how reader pages are drawn; then it serves a notice until that first read finishes. A snapshot that still carries a plan's acceptance sources inline, from before #715, is set aside the same way, and saved acceptance-source records are checked again before they serve. The dashboard also keeps two of GitHub's reads beside the snapshot: each issue's comments as of the issue's last update, and each merged pull request's head and whether its gate passed. So the first read after a restart asks GitHub only for what changed since the last run, rather than every issue's comments and every merge again. A damaged file keeps nothing, and the first read reads everything ([D-0368](../decisions/journal/D-0368.jsonl)).

## Factory activity

The page reads the factory's state, each card's stage, the proposal it asks to ratify, its modeled options and its comparison, only from markers the repository's factory posted itself, as the factory reads only its own. The watcher names the account it posts as in its status file: its App's bot, or gh's user when it runs without an App. A marker anyone else posts, a person or another App, drives nothing, and a repository whose account no watcher has named shows no factory state rather than trusting any commenter. People's commands still count from people's own comments ([D-0365](../decisions/journal/D-0365.jsonl)).

A plumbing plan waiting for ratification lists its summary, files, tests and execution metadata. Its exact acceptance files load only when someone opens **Read acceptance sources**, from a URL keyed by the proposal's full hash, and only for a complete proposal the repository's own factory posted, so the page's regular poll stays small. [Dashboard acceptance sources](factory.md#dashboard-acceptance-sources) gives the contract ([D-0388](../decisions/journal/D-0388.jsonl)).

The live dashboard gives each running step its own card, with its activity, tool calls and stretches of thinking. A running Codex card with no completed reasoning item and no `turn.completed` event shows **Pending**, with the explanation "reported when the run ends" (`thinkingPending` in the live JSON), without a numeric thinking count or numeric thinking legend. A completed reasoning item clears Pending and shows the existing estimate from reasoning length, including a zero estimate. A whole `turn.completed` event also clears Pending; absent reasoning usage leaves the current total unchanged, and any estimate remains an estimate. Pending also clears when the agent or step ends ([D-0295](../decisions/journal/D-0295.jsonl)).

A Codex card's thinking total sums the `usage.reasoning_output_tokens` reported by completed turns, counting each whole transcript line once. The first reported count, including zero, replaces any estimates. The thinking statistic and total legend then show full integers without an approximation sign (`thinkingExact` in the live JSON). During later turns the total stays at the last reported sum while the card shows the current activity; refreshes and the end of the step retain that sum.

Reasoning items still appear as timed thinking stretches with their own estimated tokens, and later items don't inflate a reported total. Once reasoning or completion clears Pending, later turns or agent sessions in that transcript never restore it; neither do refreshes, rereads or trimmed timeline marks. Each card keeps its own counts and pending state, and a replaced transcript starts fresh. Claude Code keeps accumulating its streamed estimates without Pending. The public view publishes counts, times and paths inside the agent's copy only, never commands, agent words, output or reasoning text ([D-0051](../decisions/journal/D-0051.jsonl), [D-0116](../decisions/journal/D-0116.jsonl), [D-0136](../decisions/journal/D-0136.jsonl), [D-0159](../decisions/journal/D-0159.jsonl), [D-0160](../decisions/journal/D-0160.jsonl)).

The watcher gives every draft or build invocation its own directory, including retries within the same second, and publishes its basename in the step's status as `run` after creating it and before starting the agent. The activity strip and banner checks read only that named run under the selected watcher and issue. A new step starts without a run; an absent run, directory or required file shows no activity or checks from an earlier run. Directory names are opaque identities, so their timestamps, sort order and modification times never select a run ([D-0166](../decisions/journal/D-0166.jsonl)).

When a draft's or build's step ends, however it ended, the watcher records when, in its status file, with the step's start, run, agent and the time limit its agent ran under, apart from the steps it's running. It keeps the steps that ended last, and every one that ended at that same moment, through heartbeats, restarts and its own shutdown, until a later one ends. Once none of a repository's steps is running, those are its cards, whether or not a page was open when they ended and whether or not the dashboard has restarted since: the latest end any of the repository's watchers recorded, running or stopped, in whatever order their work directories come, each tie read from its own watcher's run. Running cards still follow the lease holder or the working watcher. A finished card stops at its recorded end and keeps its run's checks, and its heading says only that the step ended, as `Build step ended`, since the attempt may have stopped or failed. A step that just disappears, a transcript or a page read never supplies an end, and a step that starts on the same issue still has no run until its own directory exists.

While a step runs, its live card comes right after the headline, in full. Once every step shown has ended, what needs a person comes first, and each finished step follows it folded to its heading: what it was, for which issue, and when and how it ended. **Show the run** opens that card, and **Hide the run** folds it again.

Every watcher's drafts and builds also keep their agent's public activity, the counts, times, tool kinds and paths inside its copy that the card shows, in the run's `activity.json`. The watcher reads each whole event as the agent's backend writes it, with the live view's own checks, while the workspace still holds what it names, and saves what it has read each time a run returns, however it ended, before the workspace is cleaned up. Events from a fallback, or from a plumbing build's repairs, add to it, each once, and deleting or renaming files can't take back what earlier events showed. Events as large as the agents' readers take, 64 MiB, count like any other, and a review, which only reads, writes a transcript of its own and never touches it. So a finished card keeps its file paths and sizes after the workspace is gone, without a page having read the transcript; a run that saved nothing is read from its transcript as the live view reads it. Finished cards never show shell commands, even at `/act`. The live view, like the saved activity, counts a fallback's or repair's Codex items once, though each run of Codex numbers its items afresh. This is [#269's ratified plan](../.invariant/plans/issue-269.json). [D-0192](../decisions/journal/D-0192.jsonl) records its decision: watcher-recorded ends, @gitdek's choice of the latest finishers and the saved activity ([D-0051](../decisions/journal/D-0051.jsonl), [D-0116](../decisions/journal/D-0116.jsonl)).

At `/act`, behind Cloudflare Access, **Show shell commands** displays each running step's shell invocations verbatim beside its activity strip, with their existing kind and start/end times. It starts off on every page load. Turning it off, losing access, ending a step or replacing its run clears the display, and a late response cannot restore it. Commands are inert text, with no tool output or reasoning, and retained only for the strip's bounded recent window. Only an authenticated `GET /act/api/live.json?commands=1` includes them, with `Cache-Control: no-store`; the default private response, public responses and agent listener never include command text. This private view follows [#236's ratified plan](../.invariant/plans/issue-236.json), an exception to [D-0116](../decisions/journal/D-0116.jsonl) for this page only ([D-0165](../decisions/journal/D-0165.jsonl)), behind the existing [Access boundary](../decisions/journal/D-0065.jsonl).
