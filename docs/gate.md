# The gate

What the gate's receipt claims about the code, and how a project proves a model's invariant at every size. [The README](../README.md#the-gate) lists every check the gate runs, and [the Python page](python.md) covers existing Python applications.

## What a receipt claims

For projects without explicit components, code assurance comes from successful results: **proved** requires a successful proof naming at least one function; otherwise successful agreement or conformance establishes **tested against the model**; otherwise the code is **unchecked**. The gate records that assurance in JSON. Discovering source functions or passing a build establishes neither proof nor model testing. These claims are separate from the gate's pass or fail result: a failed check still fails the gate, while an unrelated failure does not erase successful evidence.

Markdown receipts and the dashboard derive these claims from evidence even when an older JSON report contains a stale assurance label. **Proved at every size** additionally requires a successful check one size larger. The dashboard says **tested in every state** only for successful exhaustive conformance with positive, matching visited and model state counts and no failed attempt check. A failed attempt check still leaves evidence for the transitions that conformance successfully checked. This correction builds on the tool-output receipts in [D-0013](../decisions/D-0013-slice-plan.md), the proof and conformance paths in [D-0024](../decisions/D-0024-checking-typescript-and-python.md) and [D-0031](../decisions/journal/D-0031.jsonl), and the larger check in [D-0070](../decisions/journal/D-0070.jsonl).

Python application receipts retain the first collector failure in an execution's optional `harness_error`, with full normalized context in `diagnostics` ([#801's ratified plan](../.invariant/plans/issue-801.json)). Caught errors, exception chains, poisoned operations and terminating cleanup preserve that first cause. The affected conformance result and an actually executed run one size larger carry it too. **What failed** names the target, check and invocation for ordinary and larger executions and shows the first cause; it does not derive the cause from the last lines of a traceback. The full execution record retains the tracebacks. All application names and diagnostics render as literal text in both explicit-component and legacy receipts.

These diagnostics authorize no observations and do not enter execution fingerprints. Failed or incomplete observation streams retain no accepted prefix, while successful independent executions keep their evidence. Collector errors cannot become application refusals: [D-0279](../decisions/journal/D-0279.jsonl)'s exact declared-refusal and named-action checks still apply, and undeclared application exceptions still fail. The watchdog deadlines and stopped-before-sealing diagnostics from [D-0356](../decisions/journal/D-0356.jsonl) remain. [The Python execution reference](python.md#existing-python-application-foundation) describes the execution API and observation trust boundary.

## Current bug replay

[#857's ratified plan](../.invariant/plans/issue-857.json) separates **caught in the model** from **replayed against code**. A bug's optional ratified `code_behavior` is `current` or `hypothetical`. Omitted classification remains valid for old locks with unchanged serialization and proposal hashes. Legacy bugs say exactly **not replayed: not classified**; hypothetical bugs say **not replayed: hypothetical**. Both still have to be caught by the existing model-strength checks, and neither requests replay or contributes replay counts.

Each current bug in a driver-based gate has a mandatory obligation, even when sampling has no budget left, a driver or adapter is missing, or the driver declares exhaustive exploration. This includes ordinary TypeScript and Python drivers and existing applications, with legacy or explicit component selections. **Execution adapters are not delivered in this step.** These gates therefore fail current obligations with `replay-unavailable`; no public gate option accepts supplied successful replay evidence. The subsequent parent-plan steps must supply execution adapters. Go's proof, agreement and exploration paths keep their existing meaning. A model-only check of a project prepares pending requests without executing code, claiming replay or changing the model verdict. A draft's own check does the same, staged in its project's language, and refuses the draft while a current bug's path can't be prepared for a reason the drafter can fix ([#910](https://github.com/gitdek/invariant/issues/910)).

A repository's CI runs the gate it pins. A gate from before this change reads a lock that classifies a bug without the classification, so the proposal hash it computes isn't the one a person ratified, and its ratification check fails. Move a repository's pin to a gate with this change before its factory drafts with one.

The gate retains each bug's fresh TLC result independently, including every trace state and its loop target or stuttering marker, whether or not `-out` is set. It checks that exact path rather than searching for a shorter substitute. A generated TLC check establishes Init, every exact edge under Next or the named bug, the expected final violation, and exactly one action-and-argument interpretation per edge. Display labels are never action evidence. Missing, duplicate, malformed, ambiguous or nonmatching edge evidence yields no executable request. Nor does a path TLC can't attribute step by step, and the refusal names the step:

- A step that no single operation takes (`replay-ambiguous-edge`). The refusal lists each operation that takes it, with its arguments. The usual cause is a bug's operation that can take a step an action of Next takes too, so write a bug's operation to be enabled only where no action of Next takes the same step: a bug that drops a guard states the guard's negation.
- A step whose operation could, with the same arguments, have reached another state (`replay-unsupported-action`). Its body chooses part of its next state where no argument names the choice, and code under replay couldn't be told which way the step went. TLC decides this at the step's own state, so it finds a choice behind another name, in a disjunction or in a set, and passes an `\E` that only guards after the body's first conjunct.
- An operation whose definition begins with `\E` over anything but a named operation (`replay-unsupported-action`), wherever it stands in the model. This one is refused by its text: write its guard first, or give the choice a name.
- A step that binds a variable named like a constant or a model value (`replay-unsupported-action`).
- A model that defines `Cardinality`, `Len` or `PrintT` itself, which the generated check takes from the standard modules, or that uses `RandomElement`, `JavaTime`, `TLCGet` or `TLCSet`, none of which gives the same answer twice (`replay-unsupported-model`).

The check declares each model value itself, to write the path's states, and writes the ratified bounds ahead of them. TLC orders model values as its configuration introduces them, and `CHOOSE` follows that order, so the check reads a model's `CHOOSE` as the run that made the counterexample did. Version 1 refuses temporal counterexamples with `replay-unsupported-temporal`, retaining their infinite-behavior information: a finite lasso prefix cannot prove liveness.

The version 1 contract is available for subsequent adapters:

| Record | Required evidence |
| :-- | :-- |
| `BugReplayRequest` | Version, stable content ID, fresh invocation ID, complete ratified bug statement, proposal hash and owned checked path |
| `ReplayPath` | Module, bug pin, expected violation and kind, specification, exact main/include hashes, ratified bounds, Java image and jar hash, every ordered state and action/argument edge, first offending edge and temporal markers |
| `BugReplayResult` | Version, request and invocation IDs, outcome (`complete`, `refused`, `reproduced` or `failed`), exact initial state and ordered calls |
| `BugReplayCall` | Index, action, typed arguments, before/after states, actual dispatch, outcome (`returned`, `refused` or `failed`) and any exception/error |
| `BugReplayObservation` | Factory-owned actual-call transcript with matching identities and initial state, process start/completion and exit status, independently supplied by the execution adapter |

Replay values distinguish booleans, exact integers, strings, model values, sets, ordered sequences, records and functions with typed keys. Sets and entries canonicalize; sequences preserve order. JSON and TLA+ round trips retain the types. Malformed or ambiguous values cannot become executable TLA+; the existing display parser keeps its separate behavior.

`NewBugReplayRequest` validates the path's binding and owns its inputs. `CheckBugReplay` evaluates supplied records without attaching gate evidence. Success requires the exact initial state, every setup call in order with its exact successor, then an actually dispatched offending operation. Code need execute only through that operation; the full forbidden suffix remains retained when the violation occurs later. Reproducing the forbidden successor fails. A normal refusal must be independently observed, complete without an exception and leave state unchanged. A returned alternative or refusal must pass TLC against the same source snapshot, bounds and tools: the safety specification permits Next or stuttering, and the expected invariant must hold. Skipped or reordered setup, early stops, missing dispatch, forged refusals, unrelated exceptions, changed paths, stale identities and substituted model/includes/tools fail. States and arguments are compared by the values they hold, so an adapter's JSON may write an empty argument list as `[]` or `null` and list a set in any order; a malformed value equals nothing.

JSON exposes each bug's classification, retained replay evidence and derived `replay_status` with `status`, `label`, `required` and `replayed`. A replay whose status says `complete` or `refused` without its request, result and observation, or without having passed, reads `incomplete`. Why a path couldn't be prepared is kept as the refusal's first line, with no directory of the machine that ran it. Markdown and dashboard cards show the model catch separately from pending or failed replay, counting no unavailable obligation as replayed. Independent model, conformance and proof evidence survives a replay failure. Fingerprints bind classification, the complete stable request/path/tool/bounds evidence and result/observation records, excluding fresh invocation IDs and private trace paths. Pinned-TLC extraction regressions run in the existing `integration` lane; unchanged legacy Python admission/design-obligation fixtures keep all their refusal cases.

## Sampled state coverage

Under [#802's ratified plan](../.invariant/plans/issue-802.json), both recording APIs count distinct canonical states actually referenced by trace visits, initial states or attempt endpoints. Repeated visits and canonically equal values count once. Initial-only states and unchanged attempts count; unused state-table entries do not. Recorded steps and distinct checked transitions retain their separate counts.

Each numerator is compared only with that check's distinct reachable model-state count at the same ratified bounds. A missing per-check denominator is never filled from the design total; a conflicting positive design total makes ordinary or Python application coverage unknown. An explicitly unsuccessful model exploration cannot supply a denominator, even when its count matches the visited count: ordinary and Python coverage remain unknown, with successful conformance still checked and qualified as sampled. A nonempty design outcome must be `passed` with `design.passed` true; old reports that omit the outcome still use their per-check counts and the consistency rules. Component checks qualify from their own model, matching bounds and validated provenance. Invocations, different models, larger-bound checks and replay evidence are never added into a project share.

Report and dashboard project JSON add a `coverage` array, empty when no conformance result exists. Each ordinary result, Python invocation and attributed component check gets its own record:

| Field | Meaning |
| :-- | :-- |
| `source` | `conformance`, `python_application` or `component` |
| `target`, `check`, `invocation` | The original identities where applicable; omitted for ordinary conformance |
| `mode` | `sampled` or `bounded-exhaustive`; unavailable component mode remains empty |
| `states`, `model_states` | Original integer counts, including invalid values retained for diagnosis |
| `checked` | Successful conformance evidence, independently of the overall gate verdict and attempt coverage; component evidence must qualify from its outcomes and provenance |
| `status` | `partial` for positive visited counts below the positive model total, `full` for exact positive integer equality, otherwise `unknown` |
| `sampled` | True for a successful check whose coverage is partial or unknown |
| `fraction`, `percent` | Exact ungrouped fraction and truncated percentage strings; both empty for unknown coverage |

Failed checks and nonpositive, absent, conflicting or impossible counts have unknown coverage and no percentage. `2/5` displays as `40%`, `3/11` as `27.27%`, and `999999/1000000` as `99.99%`. Percentages truncate at two decimal places, removing trailing zeroes; integer arithmetic avoids floating-point rounding and multiplication overflow, including at the int64 limit. A tiny positive share can display `0%`, but its exact fraction remains visible. Full coverage is decided by integer equality, never the displayed percentage. JSON consumers should display the strings directly, since JavaScript numbers cannot represent every int64 count.

Markdown puts **sampled** immediately beside a passing headline and each applicable ordinary, Python or component conformance result. Dashboard cards, grouped implementations, tables and script-free evidence pages do the same on public and `/act` views, showing every applicable check's fraction and percentage or **coverage unknown**. These are detached views derived afresh from original evidence, even for old JSON with stale assurance flags. Serialized `coverage` claims are ignored. Report and reader identities use their original evidence encodings, excluding derived display metadata while still binding checked counts; rendering and JSON round trips preserve archived evidence fingerprints.

The coarse `Report.CodeAssurance` and `Claim` categories remain unchanged. Independently qualified proofs retain their claims beside sampled conformance. Full state coverage from a non-exhaustive sample grants no proof, exhaustive exploration, transition coverage or attempt coverage. Ordinary full exhaustive Markdown rows retain their exact original wording; their new JSON and dashboard views include the full fraction and percentage. Every-state/every-step requirements remain: failed attempt checks still block the claims they blocked before, checked transitions survive, and failures still fail the overall gate.

This display rule for [#789](https://github.com/gitdek/invariant/issues/789) rests on [D-0024](../decisions/journal/D-0024.jsonl), [D-0029](../decisions/journal/D-0029.jsonl), [D-0043](../decisions/journal/D-0043.jsonl), [D-0082](../decisions/journal/D-0082.jsonl), [D-0088](../decisions/journal/D-0088.jsonl), [D-0163](../decisions/journal/D-0163.jsonl), [D-0170](../decisions/journal/D-0170.jsonl), [D-0185](../decisions/journal/D-0185.jsonl), [D-0122](../decisions/journal/D-0122.jsonl) and [D-0294](../decisions/journal/D-0294.jsonl). Validation includes the affected Go suites, installed-Chromium public, `/act`, grouped and table checks, documentation checks, and existing PR CI integration and affected real Python/TLAPS lanes; those CI lanes stay in this change's validation, with no CI changes or follow-up deferral.

## Reader artifacts

[Modeled option previews](statecharts.md#modeled-alternatives) use the same model gate, complete graph, invariant replay and hiding checks, one isolated source snapshot per option. A whole-request check consumes one allowance and reports independent failures together; a failed alternative blocks publication without erasing healthy siblings' diagnostics or evidence. Previously authorized choices come from the caller, never from an option's derived output.

Preview exports under `previews/<fork>/<option>/` contain `preview.json`, model-only `receipt.json` and `receipt.md`, matching `reader.json` and a drawable `reader.svg`. The exact option IDs, words, candidate rules, sources, bounds, choices, tools and computed evidence are bound separately from ordinary verification fingerprints. Mermaid and native script-free SVG label the alternatives unratified and their rules candidates. Above 500 states the faithful size limitation replaces the chart. No preview supplies ratification or code evidence. Export reuse clears stale alternatives; checking the selected project recomputes from its final files and omits all preview metadata.

Modeled receipts recompute a reader chart from a snapshot of the checked model, sibling TLA+ includes, lock and saved `.invariant/view.json`, using complete bounded TLC exploration and invariant replay. The [reader format and provenance](statecharts.md#verification-receipts) describe the optional version-1 JSON record and its separate fingerprint. Reader data never changes verification fingerprints, pass/fail, assurance, locks or proposal identities.

The optional `.invariant/comparison.json` retains the [checked proposal comparison](statecharts.md#proposal-comparisons). Synthesis carries its original project bytes and discards agent replacements; verification captures it before checks and validates both sources, identities and deltas. It remains `Reader.comparison` beside the recomputed final-model `Reader.chart`. Source differences are explicitly labeled in Markdown and the native SVG companion. Both baseline and candidate identities, bounds, view changes and displayed-scope qualifications remain intact. A damaged comparison gets a separate diagnostic while a healthy final chart remains available. Neither absence nor damage changes verification identity or assurance. Reader output reuse removes stale companions and project writing clears obsolete comparison provenance.

`verify -out DIR` saves `receipt.json`, `receipt.md`, `reader.json` and, for a drawable chart or a retained proposal comparison, `reader.svg`. Synthesis and the factory use the same writer in their `gate/` directories, recomputing from the final model while retaining the original project's view and includes. The Markdown includes literal-safe Mermaid, exact rules, hidden steps, unavailable actions, counts and bounds. The standalone SVG renders offline through the native Go API, without scripts or external resources. Existing CI archives contain the whole output tree, including these files. Directory reuse clears obsolete reader files; filesystem output errors still fail output.

All ordinary graphs through 500 reachable states are supported. Larger graphs carry a `too_large` report with actual count, limit and tool/bounds provenance. Missing views and older reports explicitly explain that no reader chart is available until a view is supplied and verification reruns. Malformed views and graph, replay or render failures produce separate diagnostics without partial charts or a changed gate verdict. A chart of a passing model can accompany a failed build; it adds no proof claim. Plumbing remains chart-free.

## Conformance recordings

Under [#559's ratified plan](../.invariant/plans/issue-559.json), `conformance.CheckReader` takes the same arguments as `Check`, with an `io.Reader` in place of the recording's `[]byte`. `Check` is a compatibility wrapper. The checker reads incrementally, preserving exact canonical state equality, first-seen identities, JSON validation precedence and messages, counts, legacy stuttering, declared named-action outcomes and tried-step coverage.

Each invocation owns private temporary disk storage. Canonical state text is stored once, with readable diagnostics derived when needed. Memory holds small fixed-size state, transition and attempt indexes and original-ID mappings, active windows and bounded working storage. Variable-size recording contents, including a state's tried-action set, stay on disk outside active windows. The indexes grow with the number of entries; the checker does not retain the full recording's text in memory. An individual state, attempt or model need not fit a fixed byte ceiling.

Temporary disk grows with the recording during syntax validation and incremental decoding, then with distinct canonical states, attempts and tried-action instances, plus active generated modules and model copies. Init checks use windows of at most 1,000 starting states, ordinary Next and strict declared-outcome checks at most 2,000 steps or attempts, and tried checks at most 1,000 states. The checker generates windows lazily, with at most four running and no more than `GOMAXPROCS`, retaining no closure, cancellation function or decoded data per future window. Each run gets isolated regular-file copies of the model modules. Sorted transitions and original attempt order preserve the earliest failing window's diagnostic even if a later failure finishes first. The Python application's runner executes these windows in order, including Init, so its evidence keeps a deterministic prefix of actual invocations.

Input, storage and cancellation failures return operational errors without successful or partial conformance evidence. Cancellation stops further reading, iteration and scheduling; started checks finish or cancel before the checker returns. Every exit closes and removes its private storage and copied modules. The caller retains ownership of its reader, recording and model files, and independent invocations have separate stores. A semantic tried-step failure still retains successful transition evidence as described above.

Under [#569's ratified plan](../.invariant/plans/issue-569.json), part 2 of #549, `verify.Run`, including the factory's in-process gate, consumes owned file recordings through `CheckReader`. Go explorers with `Try`, ordinary Python and TypeScript drivers, and existing TypeScript drivers transfer their completed recording out of the sandbox before its workspace is removed. The recording stays available through conformance, then is closed and removed. Early gate errors, semantic failures and cancellation also remove it. Waiting recordings and future batches hold no open descriptors. Absent evidence keeps the producer's diagnostic; a present empty or malformed recording reaches the checker's validation. Go without `Try` keeps agreement alone. Direct `Language.Check` calls still return `Evidence.Traces` bytes and remove their temporary files before returning.

Sampled and explored existing Python applications convert their authenticated observations into an owned recording incrementally. Sampled lifecycles retain run order even when observations interleave. Explored recordings deduplicate raw state JSON on disk, comparing complete keys after hashing and assigning first-seen identities. Conversion preserves exact integers, module list-to-sequence semantics, replay filtering and declared outcomes, without changing ordered raw receipt observations, invocation identity, hashes, provenance or JSON-round-trip fingerprints. Scratch storage is removed on success, conversion or write failure and cancellation. Explicit byte conversion callers use the same writer; the gate holds neither a second observation tree nor a recording-sized JSON buffer.

The isolated acceptance workloads use `GOMAXPROCS=1`, `GOGC=100`, no Go memory limit and one TLC slot. End-to-end Go Try and ordinary TypeScript gates, including successful and late semantic-failure checks, are held to one **192 MiB ceiling on the Go heap they keep** at both 32,768 and 65,536 distinct states padded with 8 KiB each (256 and 512 MiB of payload). What a gate keeps is the most live heap any collection marks during the run, and a run with no collection fails. The peak including garbage the collector hasn't freed yet depends on when it runs: identical runs of the 65,536-entry late-bad Go case measured 57, 212 and 65 MiB. Locally, quiet runs kept 27 to 34 MiB and runs under CPU contention up to 65 MiB. That peak is reported beside the kept heap but not judged. `TestGateRecordingKeptHeapIsStable697` repeats that case three times and reports the spread of both ([D-0380](../decisions/journal/D-0380.jsonl)). Many distinct declared refusals over one state use the same ceiling and retain exact attempt counts. These checks substitute external commands while running the production gate, handoff, decoder and conformance checker. The Python converter's separate synthetic workload doubles 32,768 to 65,536 observations with 1,024-element module lists and uses a **96 MiB additional peak heap ceiling above already-retained receipt evidence**. A passing isolated run measured approximately 6 and 12 MiB additional heap for sampled conversion and 23 and 45 MiB for explored conversion, respectively. It exceeds the collector's per-execution event limit; authenticated end-to-end application fixtures separately check transport and receipts. These are workload ceilings, not constant-memory guarantees for arbitrary values or total Python gate memory.

Compact indexes still grow with states, transitions, attempts and sampled observation spans. Temporary disk is proportional to the recording and conversion keys and values, in addition to the checker's storage and active model copies. TLC containers, driver processes and Python's retained raw receipt evidence have separate costs; the heap ceilings exclude child processes. TLC's shared budget and existing stall and memory retry policies below remain intact. The conformance foundations are [D-0029](../decisions/journal/D-0029.jsonl), [D-0047](../decisions/journal/D-0047.jsonl), [D-0082](../decisions/journal/D-0082.jsonl), [D-0085](../decisions/journal/D-0085.jsonl), [D-0088](../decisions/journal/D-0088.jsonl) and [D-0090](../decisions/journal/D-0090.jsonl); [D-0329](../decisions/journal/D-0329.jsonl) records part 1's bounded-storage policy. Python's authenticated observation and gate foundations are [D-0183](../decisions/journal/D-0183.jsonl), [D-0185](../decisions/journal/D-0185.jsonl) and [D-0199](../decisions/journal/D-0199.jsonl). [D-0333](../decisions/journal/D-0333.jsonl) records #569's evidence ownership. PR CI runs the affected Go tests and real Python and TLAPS opt-ins; Docker/network checks unavailable to the offline build remain merger work.

## TLC resource budget

All workload containers launched through Docker `run` or `create`, including TLC, Gobra, Nagini and TLAPS, default to **4 CPUs per container** under [#622's ratified plan](../.invariant/plans/issue-622.json). The host setting `INVARIANT_CONTAINER_CPUS` accepts finite decimal counts of at least `0.01`; unset or empty selects `4`. Invalid values fail before workload launch or its image acquisition with a named configuration error, while cleanup remains available. Explicit CPU limits are preserved: the Python application executor still has exactly **1 CPU**, 512 MiB and 128 processes. Memory, process, heap, isolation, concurrency, cleanup and deadline rules stay in force.

This is a per-container quota, not an aggregate limit across checks or gate processes. It does not limit Docker-managed image-build workers such as BuildKit. Both coding-agent backends explicitly carry the host setting into their check, test and gate MCP servers. Apply it to the watcher and dashboard service environments and CLI shell, then drain and restart the watcher, restart the dashboard and start new CLI/MCP processes; existing processes and containers keep their earlier configuration. The [factory page](factory.md#container-cpu-limits) gives restart details, measurement commands and pending merger evidence. [D-0350](../decisions/journal/D-0350.jsonl) records the policy, under D-0105 and D-0122, preserving the resource and cleanup decisions below; affected real Python and TLAPS suites remain PR CI checks.

Under [#497's ratified plan](../.invariant/plans/issue-497.json), each gate invocation shares one TLC budget across full and model-only verification, existing Python applications, conformance batches, the check one size larger and stall retries. Independent checks wait for capacity and still report when another check fails. Successful checks keep their configurations, evidence, result order and receipt fingerprints.

The gate reads `NCPU` and `MemTotal` from the selected Docker daemon, including when the client selects a remote daemon. It reserves a quarter of that memory and permits at most one slot per CPU and per available 2 GiB. Each normal slot has a 2 GiB container and a 1536 MiB maximum Java heap. On smaller machines, one container uses the available memory rounded down to whole MiB; known capacity below a 256 MiB container is refused. If discovery fails, times out or returns malformed data, or either capacity is unknown, the fallback is one 1 GiB container with a 768 MiB heap.

`invariant verify -tlc-parallel N PROJECT` and the optional `verify.Options{TLCParallel: N}` argument to `verify.Run` and `verify.RunModel` can lower this concurrency ceiling. Zero, the default, selects automatically; a positive value cannot raise the computed ceiling, and negatives are rejected before tool setup. The limit changes scheduling, not what is checked.

Every TLC container has explicit `--memory` and equal `--memory-swap` limits, disabling extra swap, and `-Xmx` sets its maximum heap to three quarters of its memory limit rounded down to whole MiB. Standalone runners without a `Budget` use the 1 GiB container and 768 MiB heap defaults. Graph dumps use the same limits and admission control.

Waiting for the first slot consumes neither the silence window nor `Runner.CheckWithin`'s per-check execution allowance. The caller's overall deadline still applies while waiting and running. Cancellation of queued work starts no container and returns an error wrapping the context cause. An admitted check retains its slot until Docker cleanup completes, including through an identical stall retry. All attempts and waits for a memory retry share the original execution allowance and caller deadline.

Java `OutOfMemoryError`, `Java heap space`, `GC overhead limit exceeded` and TLC's memory frames 1001, 1002 and 1003 produce operational failures naming the check. Under [#552's ratified plan](../.invariant/plans/issue-552.json), this also includes message 1000 reporting `java.util.concurrent.ExecutionException` with an `OutOfMemoryError` cause, including `GC overhead limit exceeded` or `Java heap space` on a separate colon-prefixed line. The cause may follow the exception on the same line, and both LF and CRLF reports are recognized. These diagnostic reports override incomplete success and counterexample output and never trigger a stall retry. Similar text in module or action names, trace values, or unrelated exceptions keeps its ordinary result and earns no memory retry. [D-0325](../decisions/journal/D-0325.jsonl) records this rule.

Under [#578's ratified plan](../.invariant/plans/issue-578.json), step 3 of #549, a divisible conformance window that exhausts Java memory finishes cleanup, releases its ordinary slot and removes its generated module before regenerating two nonempty contiguous halves from the same disk store. Children use the unchanged ordinary memory and heap limits through the shared FIFO admission queue, concurrently with unrelated work. Further exhaustion halves again. This applies to Init starts, sorted Next steps, each declared accepted or refused attempt independently, and tried states. Each child contains only its local states and indexes; diagnostics still name the original endpoints, declared action, arguments and outcome, bad start or untried state. Ordinary errors, quoted trace text and exit 137 alone never split.

Recovery uses the same bounded, demand-driven scheduler as original windows, with at most four active, no more than `GOMAXPROCS`, and no more than the runner's ordinary capacity (one for standalone runners). It retains compact range descriptors on a bounded frontier, not a generated tree of modules, decoded recordings or waiting goroutines. Every child regenerates from the invocation's existing disk store. Disk holds that recording plus active generated modules and model copies; the parent copy is gone before children are generated. A later failure cannot cancel earlier recovering work. Cancellation stops further children and joins started work and cleanup before removing the store. The entire tree shares its caller's original deadline and its execution allowance from first admission. Descendants inherit any spent stall retry; siblings cannot spend one another's identical-check retry, and singleton escalation never renews it.

Under [#540's ratified plan](../.invariant/plans/issue-540.json), an ordinary model check or singleton conformance obligation may retry once with all known Docker memory left after the quarter reserve, rounded down to MiB, when that exceeds its normal slot. It finishes cleanup, releases its ordinary slot and joins the same first-in, first-out admission queue for an exclusive allocation. Earlier work drains before the larger container starts; later checks cannot pass the retry, and later retries cannot pass waiting ordinary work. Container memory and memory-plus-swap stay equal, with a three-quarter heap rounded down to MiB and the identical check configuration. The separate one-stall-retry limit never resets on escalation.

Unknown capacity, no headroom and standalone runners get no expansion. An unexpected exit 137 reports that the named check was killed, with possible memory exhaustion: the exit alone neither establishes its cause nor earns more memory. A kill caused by removing a stalled container still permits the stall retry unless its output reports Java memory exhaustion. Repeated exhaustion remains an operational failure with no partial model evidence; successful independent checks remain in the report.

Full, model-only and existing-Python gate JSON records every budgeted check attempt in `tlc_attempts`: `check`, `module`, one-based `attempt`, `memory_bytes`, `heap_bytes`, `outcome` and `message`. Each check has its own identity, including separate conformance batches using the same module, and retries keep that identity. Feedback and Markdown receipts show each allocation in MiB and each attempt's outcome and diagnostic, even when a retry recovers. This operational history is excluded from the evidence fingerprint; successful model evidence and the final verdict retain their meaning. So is an existing Python application's conformance check batch, which records how the checker scheduled its TLC work rather than what it found. The receipt still shows each batch, and a change to the batching leaves identical evidence's fingerprint alone ([#572](https://github.com/gitdek/invariant/issues/572), [D-0332](../decisions/journal/D-0332.jsonl)).

Recovery adds optional `parent_check`, `parent_attempt`, `range {kind,start,count}` and `split` fields. Ranges are zero-based half-open windows of `init`, `steps`, `strict` or `tried` units; `split=true` marks the exhausted attempt replaced by children. Child identities are distinct and portable. Detached history snapshots and JSON round trips preserve the whole tree, all allocations and diagnostics; old reports remain readable. Feedback and Markdown receipts show the ranges, parent relationships and reasons for splitting.

Existing Python applications track logical completion explicitly, retaining the deterministic actual invocation prefix on failure without interpreting directory suffixes or treating recovered intermediate failures as operational errors. `checks` contains actual completed leaf results, with their actual TLC counts. Separate `logical_checks` records bind the original `module`, `batch`, `input_sha256`, `config` and aggregate `outcome`, plus applicable failure evidence. Logical records claim no TLC counts, and exhausted parents supply no successful evidence or counterexample. Successful ordinary and explicit/legacy Python fingerprints stay independent of splitting while binding logical inputs, configurations, verdicts and counterexamples. Ordered authenticated observations, invocation provenance and coverage counts remain unchanged.

This policy builds on the pinned runner ([D-0016](../decisions/journal/D-0016.jsonl)), gate-owned configurations ([D-0017](../decisions/journal/D-0017.jsonl)), conformance batches ([D-0047](../decisions/journal/D-0047.jsonl)), the larger check ([D-0070](../decisions/journal/D-0070.jsonl)), cleanup ([D-0111](../decisions/journal/D-0111.jsonl)) and stall retries ([D-0306](../decisions/journal/D-0306.jsonl)). [D-0315](../decisions/journal/D-0315.jsonl) records the policy.

[D-0322](../decisions/journal/D-0322.jsonl) records the memory retry and its reporting, together with the [modeled gate timeout rule](factory.md#plumbing-builds), extending [D-0315](../decisions/journal/D-0315.jsonl) and [D-0306](../decisions/journal/D-0306.jsonl).

The halving policy also rests on conformance [D-0029](../decisions/journal/D-0029.jsonl), [D-0047](../decisions/journal/D-0047.jsonl), [D-0085](../decisions/journal/D-0085.jsonl) and [D-0090](../decisions/journal/D-0090.jsonl), cleanup [D-0111](../decisions/journal/D-0111.jsonl), Python evidence [D-0185](../decisions/journal/D-0185.jsonl) and [D-0199](../decisions/journal/D-0199.jsonl), memory classification [D-0325](../decisions/journal/D-0325.jsonl) and disk ownership [D-0329](../decisions/journal/D-0329.jsonl). ## Silent TLC checks

Under [#470's ratified plan](../.invariant/plans/issue-470.json), `tlc.Runner.Check` stops and removes a TLC container after fifteen uninterrupted minutes without stdout or stderr, including before its first output. It then runs the identical check once more in a fresh container. Any output bytes restart the silence window, including bytes without a newline on either stream. A check that keeps printing can run as long as its caller allows. `Runner.SilenceTimeout` is a `time.Duration` override for short tests; zero or a negative value uses fifteen minutes.

Both attempts share the caller's original context and remaining time. Cancellation or deadline expiry takes priority over a stall, stops and removes the container without another retry, and returns an error wrapping the context cause and identifying the check as cut off. An already ended context starts no container. The first container is removed before the retry starts.

A second stall returns a `Failed` result whose message says `TLC stopped making progress` and includes the last twenty lines of that attempt's combined stdout and stderr. Completed checks keep their outcomes and diagnostics, except that confirmed memory exhaustion can earn the separate larger retry above. After a first stall, only a completed attempt supplies evidence.

These rules build on the pinned TLC runner ([D-0016](../decisions/journal/D-0016.jsonl)), container cleanup ([D-0111](../decisions/journal/D-0111.jsonl)), and keeping the specification and reference pages current ([D-0122](../decisions/journal/D-0122.jsonl), [D-0294](../decisions/journal/D-0294.jsonl)). The silence-and-retry policy is [D-0306](../decisions/journal/D-0306.jsonl).

## How the gate reads a model

A pin is the hash of a ratified statement's text and of every definition it depends on. The gate finds that text itself, and TLC then checks the model with its own parser, SANY, so a pin holds only where the two read the same text. The gate reads a module the way SANY does and refuses one it can't read exactly, naming the line and what to write instead ([#812](https://github.com/gitdek/invariant/issues/812), [D-0423](../decisions/journal/D-0423.jsonl)).

- **Strings and comments.** A string runs to its closing quote on the same line, a `\*` comment to the end of its line, and a `(* *)` comment, which nests, to its matching close. A comment marker inside a string is text, and so are a quote and the other comment's markers inside a comment. A definition's canonical text, which its pin hashes, drops comments, collapses the whitespace between tokens, and keeps each string as written.
- **The module.** Its header is the file's first line that isn't blank, since SANY ignores whatever comes before a header. The module ends at the first `====` outside a string or a comment, which must be a line of its own. SANY reads nothing after that line, and neither does the gate, so the history the TLA+ Toolbox keeps there is left alone.
- **Units.** Every line at the left margin starts a definition, written `Name == …`, `Name(x) == …` or, for a function, `Name[x \in S] == …`, an `EXTENDS`, `CONSTANT`, `VARIABLE`, `RECURSIVE` or `ASSUME`, or a `----` separator. The lines under it, up to the next such line, belong to it, comments at the left margin included. SANY starts a definition wherever its grammar allows one: indented, after a comment, or on the line of the one before. So a unit may hold no `==` outside a `LET … IN` except a definition's own, and none of the words that start a unit. A record's field can't be named `LET` or `IN`: SANY allows that, and it would hide where a `LET` ends.
- **Not read.** `INSTANCE`, `LOCAL`, theorems and definitions of operator symbols are refused. So are a name defined twice, a character outside ASCII in a module's code, and a control character other than a tab or a line end, since SANY ends a comment at a lone carriage return.
- **Other modules.** A module may extend `Naturals`, `Integers`, `Sequences`, `FiniteSets`, `Bags` and `TLC`, and modules beside it in the project. A module beside the model is read the same way, and its definitions join the closure a pin covers, so one can't change under a pin. No module of a project may have the name of a module TLC ships or attaches its own code to: TLC would load the file in place of its own module, or run its own code in place of the file's definitions.
- **`\div`.** TLC evaluates `\div` with different code under `Naturals` and under `Integers`: where the operands have opposite signs and the quotient rounds to zero, the first gives 0 and the second -1. A model's `EXTENDS` isn't pinned, so a pinned statement, and anything it depends on, may use `\div` only in a model that extends `Integers`. Every other operator the two modules share is evaluated alike.

`TestSANYReadsAsTheReaderDoes812` holds each of these readings against the pinned TLC, in CI's integration shards: 14 modules both read the same way, 10 that TLC reads in a way a line-by-line reader would miss, and the arithmetic of `Naturals` and `Integers` side by side. An upgrade of TLC that changes one fails there before it can change what a pin covers.

A pin doesn't cover layout yet. TLA+ reads a bulleted list of `/\` or `\/` by its indentation, so re-indenting a statement can change what it means and keep its pin ([#814](https://github.com/gitdek/invariant/issues/814)).

## Model parse and semantic failures

When SANY, TLA+'s parser and semantic checker, prevents TLC from checking a module, the failed result's message includes SANY's complete error diagnostics and source locations in printed order before TLC's closing `Parsing or semantic analysis failed.` message. A misindented conjunction retains the offending item's line and column range and the enclosing list's range; undefined operators retain each module, source range and explanation. Routine parsing and progress lines are omitted.

These diagnostics reach the formalizer's check feedback, the gate's JSON and Markdown receipts, and the factory's failure posts and pull request body. Each uses its existing rendering and clipping rules; the result's message itself is not truncated. The raw unframed chunks in `Result.Printed`, outcome classification, other TLC errors and the last-twenty-lines fallback for other failures keep their existing behavior ([#450](https://github.com/gitdek/invariant/issues/450), [D-0298](../decisions/journal/D-0298.jsonl)).

## Downloads, retries and cleanup

Toolchain downloads and digest-pinned Docker pulls try at most three times, waiting one then two seconds after network failures, interrupted downloads, HTTP 5xx, 429 or CDN 403 responses, and registry failures. Cancellation interrupts the wait; failures retain the last diagnostic, and checksum or digest mismatches and permanent file-download errors stop immediately. Only checksum-verified bytes are published. Cache inspection selects the requested platform, with a fallback that checks the cached image's platform on older Docker versions; missing pinned images are acquired at their exact digest and platform before a run, through the same retry path. Failed acquisition returns its diagnostic as a startup error. Cached images, local images, explicit `--pull=never`, proxy suppression and workload arguments, stdin, output and exit status keep their behavior; builds and workloads never retry ([#433's ratified plan](../.invariant/plans/issue-433.json), [D-0016](../decisions/journal/D-0016.jsonl), [D-0178](../decisions/journal/D-0178.jsonl)).

Cancellation removes the named container before stopping its Docker client, then removes that name again after the client exits, using a bounded independent cleanup context. A cancelled command returns only after cleanup. Both Python leak checks list only `invariant-<current pid>-` containers, so concurrent processes cannot create false leaks. This extends [D-0111](../decisions/journal/D-0111.jsonl) under #433's plan ([D-0308](../decisions/journal/D-0308.jsonl)). CI runs the affected real Python and TLAPS suites ([D-0286](../decisions/journal/D-0286.jsonl)).

## Proving a model's invariant at every size

TLC checks the design within the ratified bounds, and Gobra and Nagini prove the code's operations at every size. A project can also have the gate prove a ratified invariant of the model itself at every size, with TLAPS, the TLA+ Proof System ([#360](https://github.com/gitdek/invariant/issues/360), [D-0229](../decisions/D-0229-tlaps-design-proofs.md)). The idea comes from EasyProver ([arXiv 2610.38174](https://arxiv.org/abs/2610.38174)): an agent's proof is untrusted search, and the gate alone accepts it, against a theorem the gate writes itself.

The project's manifest selects the invariant, and its proof sits beside the lock, as [`examples/05-connection-pool`](../examples/05-connection-pool) does for `NoSharedConnection`:

```json
"tlaps": ["NoSharedConnection"]
```

`.invariant/proofs/NoSharedConnection.tla` is the body of a module the gate writes. It defines an inductive invariant and proves three lemmas whose statements are the gate's ([D-0231](../decisions/journal/D-0231.jsonl)):

```tla
IndInv_NoSharedConnection == TypeOK /\ NoSharedConnection

LEMMA NoSharedConnection_Init == Init => IndInv_NoSharedConnection
BY DEF Init, IndInv_NoSharedConnection, TypeOK, NoSharedConnection

LEMMA NoSharedConnection_Step == IndInv_NoSharedConnection /\ [Next]_vars => IndInv_NoSharedConnection'
BY DEF IndInv_NoSharedConnection, TypeOK, NoSharedConnection, Next, vars, Acquire, Refuse, Release, Out, Conns

LEMMA NoSharedConnection_Implies == IndInv_NoSharedConnection => NoSharedConnection
BY DEF IndInv_NoSharedConnection
```

The gate extends the ratified model and TLAPS around the proof, then adds the only theorem that counts, `NoSharedConnection_AtEverySize == Spec => []NoSharedConnection`. It proves that by PTL from the three lemmas, and LS4 decides it. tlapm proves the rest; for the pool, SMT took all three lemmas, with no decomposition. The receipt shows it on a row of its own:

```
| Design · TLAPS | ✅ model invariant proved at every size (TLAPS) | `NoSharedConnection`: 8 obligations (1 ls4, 3 smt, 4 trivial) · tlapm `eef4b65` |
```

What the gate refuses, so a proof can only be wrong by not going through:

- A proof may not add an axiom, assumption, constant, variable, instance, module, or `LOCAL` or `RECURSIVE` definition, omit a proof, or cite TLAPS's temporal rules, such as `RuleINV1`, since the gate takes the only temporal step itself. tlapm runs with `--strict`, since without it tlapm exits 0 with obligations failed and passes over a missing proof.
- A proof may extend only TLAPS's standard modules. The receipt names any of their facts it cites, which those modules state without a proof tlapm checks here.
- Neither the model nor the proof may use `ENABLED`, `\cdot`, temporal operators, `CASE` expressions, exponents, or a set enumeration whose element is a membership such as `{e \in S}` (which tlapm reads as the empty set), and the proof may not name the PTL or LS4 backend. These are the constructs open soundness issues in tlapm touch ([tlaplus/tlapm#309](https://github.com/tlaplus/tlapm/issues/309), [#304](https://github.com/tlaplus/tlapm/issues/304), [#306](https://github.com/tlaplus/tlapm/issues/306), [#300](https://github.com/tlaplus/tlapm/issues/300), [#235](https://github.com/tlaplus/tlapm/issues/235), [#310](https://github.com/tlaplus/tlapm/issues/310)). Because tlapm names each term it abstracts for a backend by 20 bits of an unchecked hash, and a primed hidden definition is such a term, the gate also refuses a proof when two definition names, the proof's or the model's, would abstract to the same atom. The refusals are checked complete against the pinned tlapm's own known-soundness tests, so a newly known unsoundness can't slip past (the one exception, the len/DOMAIN issue [#51](https://github.com/tlaplus/tlapm/issues/51), needs an old SMT encoding the gate never selects).
- The model's spec must be `Init /\ [][Next]_vars`. It may hold no assumption or theorem, may extend only Naturals, Integers, Reals, Sequences, FiniteSets and Bags, and may not use `INSTANCE` or `RECURSIVE`.

What it proves, and what it doesn't:

- It proves the model never breaks the invariant, in any behavior, for every value of its constants. TLC's check within the bounds stays beside it.
- It says nothing about the code. What the receipt says of the code doesn't change.
- Its trust model is weaker than a kernel-checked proof's: SMT and Zenon results aren't certified, and tlapm's translation has the open issues above.

tlapm is pinned: 1.6.0-pre at commit `eef4b65`, from an unmodified copy of the release's x86_64 Linux tarball, held by Invariant's own release [`tlapm-1.6.0-pre-eef4b65`](https://github.com/gitdek/invariant/releases/tag/tlapm-1.6.0-pre-eef4b65) and pinned by SHA-256, with Z3 4.8.9, Zenon 0.8.4, Isabelle2025 and LS4, in a linux/amd64 image built on first use ([D-0269](../decisions/journal/D-0269.jsonl)). The tarball also carries a `tla2tools.jar` for tlapm's optional SANY parser, which the gate never selects, so tlapm parses with its own parser, the default. Upstream's release is rolling and replaced its asset twice on 2026-11-01, so the gate fetches that copy instead ([D-0272](../decisions/journal/D-0272.jsonl)). If its bytes ever changed, the image would fail to build rather than install another tlapm. Moving to a newer tlapm means validating its build and mirroring it the same way. To run the real tlapm tests:

```bash
INVARIANT_TLAPS_REAL=1 go test ./internal/verify -run '^TestTLAPSReal' -count=1 -timeout 30m
```

Existing Python applications can't select TLAPS proofs yet.
