# The factory

How the factory carries an issue to a merged pull request, in detail. [The README](../README.md#watch-it-take-an-issue) tells the story and lists the commands people steer it with, and [SPEC.md](../SPEC.md) is the whole current state.

## Plumbing builds

For plumbing, the factory runs formatting, vet, the tests of every touched package and the pinned acceptance tests, then has a second agent review the whole candidate against the original checkout. When review asks for changes, the same builder receives the findings in its existing workspace under the unchanged ratified plan. It gets at most two repair attempts, each followed by fresh factory checks and, only if those pass, a fresh read-only review. Only final passing checks and approval produce a ready pull request. Unresolved findings leave a draft for a person, even when a repair fails tests or runs out of time; the failure post keeps both the findings and the check failures ([#281's ratified plan](../.invariant/plans/issue-281.json), [D-0105](../decisions/D-0105-factory-takes-every-change.md), [D-0108](../decisions/journal/D-0108.jsonl)).

The agent's test tool and the factory's checks use the same plumbing sandbox ([#397's ratified plan](../.invariant/plans/issue-397.json), [D-0281](../decisions/journal/D-0281.jsonl)). It compiles each touched package once, serially, before tests start, then reuses that binary from its package directory for discovery, tests and acceptance checks. Eight workers pull top-level tests, examples and fuzz seeds from one shared queue; subtests stay with their parent. Tests with no valid recorded duration come first, sorted by package and name, followed by known tests longest first, with ties in package/name order. Measured durations survive in the build's isolated shared Go cache for later checks. They are untrusted ordering hints: malformed or stale entries cannot add, omit or duplicate a discovered test, run commands or supply results. Each discovered test is queued exactly once for the touched-test phase, and pinned acceptance tests run again individually.

The sandbox uses the pinned Python image with the pinned Go toolchain and git, no network, a read-only module cache and hostname `localhost` ([D-0110](../decisions/journal/D-0110.jsonl), [D-0117](../decisions/journal/D-0117.jsonl), [D-0189](../decisions/journal/D-0189.jsonl)). Every container starts with Docker's `--init`, whose init process reaps orphaned children ([#426's ratified plan](../.invariant/plans/issue-426.json), [D-0290](../decisions/journal/D-0290.jsonl)). Its embedded runner uses only Python's standard library. Each container has a 4 GiB memory limit and a 1,024-process limit; three simultaneous agent operations can therefore use up to 12 GiB and 3,072 processes. Compilation uses `GOMAXPROCS=2` and `-p=1`. A whole check has twelve minutes from entry, including checkout preparation, startup, formatting, vet, compilation, discovery and acceptance. The eight workers share one ten-minute test-phase budget; each invocation gets only the time left in both budgets. Neither another test nor a cold cache renews either allowance. A conservative one-minute startup reserve and fifteen-second cleanup reserve bring the delivery budget to thirteen minutes fifteen seconds, below both supported agents' unchanged 900-second tool limits.

A deadline returns a failed report and removes the container. Reports retain package and test names for passed, failed, still-running and unstarted (`not_run`) work, even when the raw log is clipped. The summary names every test that didn't pass, first, and counts a passing run's tests instead of naming them; a run that didn't pass names at most 100 passed ones, so a large package's run fits an agent's tool result. A plan's pull request quotes at most 6,000 bytes of it ([D-0282](../decisions/journal/D-0282.jsonl)). Build failures, worker failures, timeouts and interruptions fail the check while independent work continues within the remaining time. Each acceptance test keeps its own result by package and name, including when neighbors fail or another package has the same test name. Before proposing a plan, its check rejects any acceptance test that already passes, any deadline or interruption, and any unfinished acceptance evidence. Only the testing package's own reports count as a test's result: text a test binary prints before its tests start, as a `TestMain` can, stays a diagnostic and leaves those tests unstarted. Completed failing tests and completed compiler failures in the acceptance test's package, such as a new API the base lacks, remain valid evidence that the code needs the change.

The opt-in real-image gate checks cold-run capacity on a cgroup-v2 Docker host. Two simultaneous runs with fresh caches must pass; three must return within the deadline budget, with named partial failures allowed. Both waves measure kernel memory and process peaks, including compilation, below the enforced limits. Image acquisition happens before the timed runs. Run it with `INVARIANT_PLUMBING_REAL=1 go test ./internal/plumbing -run '^TestSandboxBudgetAndRealCheckout$' -count=1 -timeout 45m`. Its default assertions also run without Docker; the real-image check returns normally when it is not enabled.

The orphan-reaping acceptance test checks `--init` alongside the existing launch settings without Docker. Run `INVARIANT_PLUMBING_INIT_REAL=1 go test ./internal/plumbing -run '^TestSandboxReapsOrphanedProcesses$' -count=1 -timeout 20m` to also run a Go test in the pinned sandbox image: it waits for a child's parent to exit, kills the orphan, and requires `kill(pid, 0)` to report that the process is gone (`ESRCH`). The real-image check returns normally when it is not enabled.

## Repository check contract

Version 1 of `.invariant/repository.json` describes a repository's Go, Python and TypeScript parts, their checks, their owners and the files that supply check authority ([#461's ratified plan](../.invariant/plans/issue-461.json)). The shared `internal/repository` loader captures this contract from a caller-supplied committed base. It executes no declared commands. Plumbing on external repositories remains disabled ([D-0121](../decisions/journal/D-0121.jsonl)). Invariant continues to use its built-in plumbing runner, commands, sandbox limits and scope rules without requiring this file.

The top-level fields are `version`, `parts`, `agent_rules`, `current_state`, `trusted_paths` and `shared_paths`. `parts` is nonempty; each part has a unique `name` and `directory`, one supported `language`, an `image` pinned by `@sha256:` and a 64-digit hexadecimal digest, explicit `lockfiles` and `inputs` arrays, and a `commands` object. All paths are relative to the repository root, including a part's dependency inputs. Commands are defined to run in the part's directory. This example uses an illustrative image digest; a repository supplies its own toolchain image:

```json
{
  "version": 1,
  "parts": [
    {
      "name": "api",
      "directory": "api",
      "language": "go",
      "image": "registry.example/toolchain@sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
      "lockfiles": ["api/go.sum"],
      "inputs": ["api/go.mod"],
      "commands": {
        "install": {"argv": ["go", "mod", "download"]},
        "format": {"argv": ["gofmt", "-l", "."]},
        "lint": {"argv": ["go", "vet", "./..."]},
        "build": {"argv": ["go", "build", "./..."]},
        "test": {"argv": ["go", "test", "./..."]},
        "test_one": {"argv": ["go", "test", "./...", "-run", "^{test}$", "-count=1"]}
      }
    }
  ],
  "agent_rules": ["AGENTS.md"],
  "current_state": ["SPEC.md", "README.md"],
  "trusted_paths": ["tools/"],
  "shared_paths": [{"path": "shared/", "parts": ["api"]}]
}
```

`language` is `go`, `python` or `typescript`, and a repository may mix them. Each of the six command entries is required. It holds either a nonempty `argv` array with a nonblank executable, or a nonblank reason such as `{"not_applicable": "This application has no distribution artifact."}`, never both. `lockfiles` and `inputs` are required arrays but may be empty. The executable form of `test_one` contains exactly one `{test}` placeholder in one argument: for example, `"^{test}$"` with Go's `-run`, `"{test}"` as a pytest selector, or `"{test}"` after `npm test --`. This is literal command data for a later runner, with no shell interpolation by the loader. An inapplicable `test_one` needs an explicit reason like any other check.

The loader rejects unsupported versions and languages, mutable image tags without a digest, malformed digests, unknown or duplicate JSON keys, trailing JSON, missing required fields and contradictory commands. Part directories must exist in the base commit, and agent rules, current-state documents, lockfiles and inputs must be regular files there. Paths use `/`, are nonempty and clean, and stay inside the repository; only a part's `directory` may be `.`. Backslashes, control characters, Git metadata, globs, symlink ancestors or leaves, and gitlinks are refused. Unrelated links elsewhere in the repository do not invalidate a contract.

`trusted_paths` entries and each `shared_paths.path` select an exact file or a directory prefix ending in `/`; prefixes can reserve future files. A shared rule lists its owners in `parts`. Duplicate or overlapping shared selectors, duplicate part names or directories, and unknown owners are invalid. Nested part directories are allowed.

For each touched file, ownership is the deepest enclosing part, plus any explicitly shared owners and every part declaring that file as a lockfile or input. A root part therefore owns files outside its nested parts without also owning their code. A workspace lockfile can select several parts, even outside their directories. Changes to `.invariant/repository.json`, `agent_rules` or `current_state` files select every part. Selection returns unique parts sorted by name, independent of declaration order. New paths need not exist, deleted paths retain their base ownership, and any unowned or unsafe path fails the entire selection. An empty set of touched files selects no parts.

Ownership and trust answer different questions. Trust includes the contract itself, agent rules, every declared lockfile and input, and `trusted_paths`. Ordinary code and current-state documents are not implicitly trusted. For Invariant itself, the loader under `internal/repository/` and `.invariant/repository.json` are also in its built-in trusted base, so their changes require a person to merge them ([D-0109](../decisions/journal/D-0109.jsonl)).

`repository.Load(ctx, checkout, baseRef)` requires an explicit nonempty commit or ref and resolves it once. The resulting snapshot exposes the resolved commit through `Commit()`, independent configuration through `Config()`, committed file bytes through `ReadFile(path)`, applicable parts through `PartsFor(paths)`, and the captured trust policy through `IsTrusted(path)`. Every method stays bound to that commit. Changing the index, working tree, candidate configuration or base ref, or mutating returned configuration, parts or bytes, cannot replace its authority. `ErrMissing` means only that the contract is absent from a valid base tree; invalid configuration returns `ErrInvalid`, and invalid revisions and read failures never masquerade as missing configuration.

The loader has no automatic fallback to Invariant's built-in policy or to a modeled project. Modeled projects continue to load their own `.invariant/invariant.json` and ratified locks unchanged, with or without a repository contract. This step supplies the shared contract and ownership queries; it does not wire declared commands into the factory or relax external-plumbing, sandbox or scope restrictions. Before the next step, the merger records #461's repository-contract decision, since a plumbing build cannot write `decisions/` ([D-0105](../decisions/D-0105-factory-takes-every-change.md), [D-0122](../decisions/journal/D-0122.jsonl)).

## Retries

A retry builds a plan's failed draft again, and otherwise watches a pull request that's open, or builds again when there's none ([D-0047](../decisions/journal/D-0047.jsonl), [D-0064](../decisions/journal/D-0064.jsonl), [D-0218](../decisions/journal/D-0218.jsonl)). After a plan's build left a draft, because its agent ended its last run with an error, its tests failed or its review asked for changes, `/invariant retry` has the factory store its record that the retry replaces the draft, close the draft without merging it, so its work stays there to read, and build the ratified plan again from its ratification, on a branch of its own, review included. The new build opens a pull request of its own, ready once its checks and review pass, or a draft again, which a writer can retry in turn ([#271](https://github.com/gitdek/invariant/issues/271)). If the draft's branch, which holds the plan's ratification, is gone, the retry is answered with a note for a person instead: close the draft and comment `/invariant revise` to draft the plan again ([D-0220](../decisions/journal/D-0220.jsonl)). A retry's build on another machine that can't reach the commit holding the ratification says the same once the draft is closed, as a failure for a person, and the dashboard's card for it offers only drafting the plan again. A retry applies to the failure that was the issue's latest when it was posted, so one posted before a draft's failure post, such as a second retry queued while the first draft was open, gets a note and builds nothing ([D-0238](../decisions/journal/D-0238.jsonl)). After CI's gate failed on a pull request, or for a modeled project's draft, or a draft GitHub wouldn't mark ready after its build passed, `/invariant retry` has the factory watch that pull request again. Once CI's gate passes on its current head, it's still in scope with its ratified lock, and GitHub says it can merge it, the factory marks a draft ready and merges it at the head it checked, without running a review ([#145](https://github.com/gitdek/invariant/issues/145), [D-0249](../decisions/journal/D-0249.jsonl), [D-0252](../decisions/journal/D-0252.jsonl)). Its answer to the retry records whether the pull request was a draft or ready, and when the writer retried, and it marks a draft ready only when that answer saw it as a draft and GitHub shows no one has turned it into a draft since the retry. So a person stops a watched pull request by closing it or the issue, or, while it's ready, by turning it into a draft, even before the factory answers the retry: once CI's gate passes, the factory says once that someone turned it into a draft after the retry, and a writer's retry after that has it watch the draft after all. An answer from before #371, which records neither, watches no draft, so a person decides, and so does a draft whose events GitHub won't show, or keeps failing to show for half an hour ([#371](https://github.com/gitdek/invariant/issues/371), [D-0270](../decisions/journal/D-0270.jsonl), [D-0274](../decisions/journal/D-0274.jsonl)). A change to the trusted base waits for a person to merge it instead, and the factory doesn't mark its draft ready ([D-0109](../decisions/journal/D-0109.jsonl)). To change a plan instead, close its pull request, say what to change, comment `/invariant revise`, and ratify the new draft. After a build that stopped before it made a pull request, a retry builds the ratified proposal again. The factory's posts say which happens, and so does the dashboard: a card's retry button says what it does, such as "Build the plan again, replacing #N" or "Merge #N once CI passes", `/act` asks first in the same words and says what follows once it's posted, and the comment it posts is `/invariant retry` either way ([D-0156](../decisions/journal/D-0156.jsonl)). A failed draft's post lists the plan's files in the trusted base in its body, which a post too long for GitHub clips, and keeps its commands and what they do whole ([D-0167](../decisions/journal/D-0167.jsonl)).

## What a build may write

The builder may write the plan's named files and add new regular Go `*_test.go` regression files in packages the plan touches, including the nearest Go package owning a planned embedded asset and new packages the plan names. Staging, formatting, package tests, final copying and CI scope all honor that allowance. Existing unnamed tests, the ratified acceptance tests and plan, other production files and unrelated packages remain protected, and linked files are refused. The original checkout stays the baseline across every repair, so tests the builder adds can later be corrected or removed ([D-0107](../decisions/journal/D-0107.jsonl), [D-0110](../decisions/journal/D-0110.jsonl), [D-0133](../decisions/journal/D-0133.jsonl)). CI's scope check judges a test new against the merge base a pull request's changes come from, so a branch that changes an existing test main has since deleted doesn't count as adding one. Formatting checks only the regression tests the build added, beside the named Go files and acceptance tests, so an existing test the builder may not edit never blocks a build. Package tests count only directories that still hold Go files, so a package the plan deletes isn't tested (#298, [D-0190](../decisions/journal/D-0190.jsonl)).

## Time, usage and the provider

The initial build, fallback, repairs and all reviews contribute their turns, cost, token fields and tool calls to the same build's totals, with every transcript and test log retained. They and the factory checks share one execution time allowance; another round or fallback never renews it. Waiting for an agent account's first turn in a run remains excluded; a provider retry's waits, and the turns it takes again, count ([D-0125](../decisions/journal/D-0125.jsonl), [D-0154](../decisions/journal/D-0154.jsonl)).

When an agent's provider is briefly unavailable, at capacity, rate-limited, overloaded, failing on its side after its own retries or dropping the connection, the run tries again in the same workspace after waits of one, two and four minutes: four attempts, about seven minutes for the provider to come back. Every Codex and Claude Code run does, for drafts, plans, builds and reviews. The attempts are one run, with one time limit, and each wait gives Codex's turn back so other steps go on. They share one allowance of gate, check or test calls, which Invariant's MCP server counts before each call against a count the run itself keeps, at an address the run names in each server's configuration, since Codex filters what its servers inherit, and only what's left of Claude Code's budget and turns or Codex's steps. Usage adds up every attempt, and counts a tool call the allowance gave even when the agent's events lost it. A Claude Code attempt that ends after paid replies but before it says what it cost counts the rest of the budget as spent, a conservative estimate, and nothing retries it. Only the provider's own reported failure decides, not earlier stderr or Codex's notices that it's reconnecting, and Claude Code's own fields for the error's kind, status and cause decide before its words; an MCP server that didn't start, a usage limit or other account limit, even one Claude Code reports as a rate limit, and every other failure end the run as before. If the provider stays unavailable, the post quotes the last provider error. A draft proposes nothing, and `/invariant revise` drafting it again is all it needs. A build publishes nothing its agent left, not even a draft pull request, though the leftovers would pass, and `/invariant retry` builds the ratified proposal again, review included ([#261's ratified plan](../.invariant/plans/issue-261.json), [D-0069](../decisions/D-0069-slice-9-plan.md), [D-0138](../decisions/journal/D-0138.jsonl)).

## Merger work and CI

Reviewers put decision recording and checks that require unavailable Docker or network access under **Merger work**, and approve when those are all that remains. The merger completes those duties before moving on, since a plumbing build cannot write `decisions/` ([D-0122](../decisions/journal/D-0122.jsonl)). #281's repair, regression-test and merger-work policy is recorded as [D-0173](../decisions/journal/D-0173.jsonl). CI still runs the whole suite, and a person still merges changes to the trusted base ([D-0109](../decisions/journal/D-0109.jsonl)). CI also runs the opt-in real suites, with real Docker, TLC, Nagini, wheels and TLAPS, on every pull request and push to main whose change can affect them, and invariant/gate requires them, so reviewers don't list them ([D-0291](../decisions/journal/D-0291.jsonl)). The plumbing sandbox's real-image budget check stays merger work, since it needs a bigger cgroup-v2 host than a CI runner ([D-0286](../decisions/journal/D-0286.jsonl)).

## Plans of issues

Plans of issues can nest. A planned issue may itself become a ratified plan of issues, with no build or pull request of its own. Its parent waits until the factory records that child's whole plan as complete under its ratified hash; an unfinished or stopped child plan holds its parent. Completion carries upward through nested plans on later polls, opening each step and recording each plan's completion once, including after a watcher restarts.

## Running the factory

`-parallel` sets the number of agent slots, three by default. Drafting statements, plumbing plans or plans of issues and building modeled projects or plumbing plans all share those slots. An operation holds its slot through its reviews, fallbacks and repairs. Commands, ratifications, merges, closure handling and labels proceed while every slot is occupied, including with `-parallel 1`, and the watcher keeps polling and publishing its heartbeat ([#455's ratified plan](../.invariant/plans/issue-455.json), [D-0300](../decisions/journal/D-0300.jsonl), refining [D-0113](../decisions/D-0113-factory-works-issues-at-once.md)).

Each poll dispatches every issue that has no step running, and returns without waiting for agent capacity. A waiting step still owns its issue across polls, so it cannot start twice. It records and advertises no agent run until it has a slot, then rechecks that the issue is open and the step still belongs to the current lease tenure. Recorded results can be reused without a slot. Success, error, panic and cancellation release the slot; shutdown drains both queued and running steps. For callers of the Go API, positive `Factory.Parallel` uses this scheduling, while its zero value keeps `Poll` synchronous. Protocol and recovery checks still govern every effect ([D-0069](../decisions/D-0069-slice-9-plan.md), [D-0237](../decisions/journal/D-0237.jsonl)).

`-projects` is the directory new projects go in. `-language` is what the factory writes when an issue doesn't pick one: `go`, `typescript` or `python`. `-agent` is the coding agent that drafts and builds an issue when neither it nor its project picks one: `codex`, the default, or `claude-code`. The watcher runs only the agents `-agents` names, `codex` alone unless you add `claude-code`, so it never starts Claude Code otherwise. Codex runs on `gpt-6-astra` at `ultra`, its highest reasoning (`-codex-model`, `-codex-effort`). The factory acts as you, through `gh`. To have it act as its own bot, [set up a GitHub App](factory-app.md) and add `-app-id`. With Claude Code turned on, each of its runs may spend up to $3 of estimated cost drafting, or reviewing a plan's build, and $5 building, on your account (`-formalize-budget`, `-budget`). A build's fallback, repairs and reviews are runs of their own. A Codex run is capped by its steps (`-codex-steps`). A build whose agent the loop guard stops says why, and runs its agent once more at `-fallback-effort`, `xhigh` by default, when that's below its effort; a fallback that stops the same way fails the build. Claude Code's guard stops a run once two replies in a row end at the output limit with nothing but thinking ([D-0115](../decisions/journal/D-0115.jsonl), [D-0125](../decisions/journal/D-0125.jsonl)). Codex fails its turn itself at the first reply that reaches the model's output limit, saying `Incomplete response returned, reason: max_output_tokens`, and that's its guard's stop, never a provider's failure ([D-0257](../decisions/journal/D-0257.jsonl)). Before it takes an issue, the watcher checks that it can run its coding agent, and any other that `-agents` names and a project's manifest picks: that the agent's CLI runs and is signed in. If one can't run, it doesn't start, and says what to fix. For Codex, sign it in once to a home of its own, which its commands can't read: `invariant/codex` in your user config directory, or `-codex-home`. On macOS:

```bash
mkdir -p "$HOME/Library/Application Support/invariant/codex"
CODEX_HOME="$HOME/Library/Application Support/invariant/codex" codex login
```

Codex's commands then run under a permission profile of Codex's own: they see only the workspace, the system and Go's toolchain, reach no network, and can't read your home directory. The watcher checks that before it runs Codex, and runs one Codex run at a time.

The watcher keeps its clone and every run's transcript, checks and records in its work directory, `-work`, by default `invariant/watch` in your user cache directory. A plan's draft and build each give their checks a Go build cache of their own and remove it when they end, and a watcher removes any a stopped watcher left when it starts ([D-0233](../decisions/journal/D-0233.jsonl)).

## Recovery

The watcher takes each step as a few effects on GitHub, and it can stop between any two: a crash, a restart, a laptop going to sleep. Two watchers can also run on one repository at once.

- **The watcher runs on it.** It records each agent run and merge where every watcher can see them, and one watcher at a time holds a lease in a Git ref. It takes every effect only as the proved core allows ([#24](https://github.com/gitdek/invariant/pull/24), [#26](https://github.com/gitdek/invariant/pull/26)). A watcher that takes the lease back after another held it starts a new tenure, and a step it started before then takes no effect, except that an agent run that outlived it still has what it left recorded, its result or why it stopped, for its next step to publish if nothing answered or replaced the build since. The core sees only whether the watcher holds the lease, so the tenure check is the watcher's own, unproved ([D-0237](../decisions/journal/D-0237.jsonl)).
- **GitHub failing isn't GitHub refusing.** When GitHub fails for a moment as the factory marks a draft ready or merges, or reads a watched draft's events before it marks it ready, with a 5xx, a dropped connection, a client's timeout, a name that didn't resolve, a rate limit or gh killed mid-request, the factory asks again on the next poll, where a refusal, such as a 422 or a 405, is said on the issue at once, whatever else its message says. It asks for half an hour from the first failure, and an hour more for GitHub's primary rate limit, which resets within the hour. Then it says once that GitHub kept failing, what it was trying to do and GitHub's last answer, labels the issue for a person, and asks nothing more until a writer's retry has it watch the pull request again. It records when GitHub first failed beside the issue's runs, so the count holds across restarts and watchers. Before it says GitHub kept failing, it reads the pull request again, so a merge GitHub made whose answer was lost is still recorded as the factory's ([#376](https://github.com/gitdek/invariant/issues/376), [D-0265](../decisions/journal/D-0265.jsonl), [D-0266](../decisions/journal/D-0266.jsonl), [D-0267](../decisions/journal/D-0267.jsonl), [D-0274](../decisions/journal/D-0274.jsonl)).
- **A refusal holds the work for a writer.** When GitHub refuses one of a step's effects outright, with a 4xx other than a rate limit or a 408, such as opening a pull request, posting a proposal, opening a plan's issue, changing a label or deleting a branch, the factory records the refusal before it reports it. It quotes the effect and GitHub's own message once on the issue, labels the issue for a person, and does nothing more on it until a writer's new `/invariant retry`. Recorded runs and build results survive, so the retry publishes what was built rather than building again, and a later watcher finishes a report the first couldn't post without repeating the refused effect. Deleting a branch that's already gone isn't refused: GitHub answers that with a 404, or a 422 saying the reference doesn't exist, as after it deletes a merged branch itself ([#434](https://github.com/gitdek/invariant/issues/434), [D-0299](../decisions/journal/D-0299.jsonl)).
- **A closed issue gets its last record.** Closing an issue stops the factory's work on it: it records the close once, leaves an open pull request open, and resumes nothing queued, and a reopened issue picks up where it was. A person's merge of the issue's pull request is recorded once, whether GitHub closed the issue first or the close was recorded before the merge, and a scope check that finds an empty diff reads the pull request again, so a merge made during the check is recorded too. Each poll reads the open issues, the closed ones still carrying an active label, and the issue of each factory pull request merged since the watcher started, found among the 30 closed pull requests updated most recently. It reads no other closed issue, so a repository's history costs no API calls per poll ([#434](https://github.com/gitdek/invariant/issues/434), [D-0299](../decisions/journal/D-0299.jsonl)).
- **A retry can replace a failed draft.** For [#271](https://github.com/gitdek/invariant/issues/271), a coding agent amended the recovery model by hand, and @gitdek ratified it as [D-0203](../decisions/journal/D-0203.jsonl), and its exact proposal as [D-0210](../decisions/journal/D-0210.jsonl). Each writer's retry starts a new build, with its own agent run, which replaces the failed draft. The factory stores its record that the retry replaces the draft before it closes it, at most one of the work's pull requests is open at a time, and each build opens at most one. Each build is an attempt with its number, so the core itself refuses to count a run an earlier attempt started for the latest build ([D-0212](../decisions/journal/D-0212.jsonl)). TLC checks it in 29,725 states, for any number of retries, and Gobra proved the core again, 46 of 46 functions. A modeled project's failed draft, which a retry only watches again, was a ready pull request in the model's terms until #354 ([D-0211](../decisions/journal/D-0211.jsonl)). The watcher maps its retries onto it, and a test stops the watcher before each of a rebuild's 16 effects, from the retry's record to the merge, then starts a fresh one here or on another machine: every time, the draft is replaced once, with one successor, one build per retry and one merge ([D-0218](../decisions/journal/D-0218.jsonl)). Since [#354](https://github.com/gitdek/invariant/issues/354), the model also covers a writer's retry that watches a modeled project's failed draft again, which the factory marks ready and merges once CI's gate passes and GitHub says it can merge it, unless it changes the trusted base, ratified by hand for its exact proposal as [D-0225](../decisions/journal/D-0225.jsonl). TLC checks it in 50,941 states, and Gobra proves the core, 48 of 48 functions. The watcher maps each pull request as GitHub has it, a draft as a draft, and marks ready only a draft a retry watched as that draft, merging it only at the head whose gate passed. A draft a person made of the factory's pull request stays theirs, whether they made it before or after a retry watched the pull request: the factory says so once, and a writer's retry has it watch the draft after all ([D-0232](../decisions/journal/D-0232.jsonl), [D-0249](../decisions/journal/D-0249.jsonl), [D-0252](../decisions/journal/D-0252.jsonl), [D-0270](../decisions/journal/D-0270.jsonl)).

## How its rules changed

- **A person ratified the next change by hand.** [#271](https://github.com/gitdek/invariant/issues/271) asks that a writer's retry build a failed plumbing build again and replace its draft. A coding agent drafted the protocol's `Rebuild` step, with two invariants, three witnesses and two known bugs, checked by TLC in 25,206 states, and @gitdek ratified it as a decision, [D-0202](../decisions/journal/D-0202.jsonl). Gobra proved the core again, 22 of 22 functions. A lock ratified that way holds only for the exact proposal a person's ratification in the journal names, as one ratified on an issue holds only for the hash its comment names: CI, `invariant decisions check`, the gate and the dashboard all check it, so the lock named [D-0209](../decisions/journal/D-0209.jsonl), which ratifies the amendment's exact proposal ([D-0204](../decisions/journal/D-0204.jsonl), [D-0208](../decisions/journal/D-0208.jsonl)), until [#428](https://github.com/gitdek/invariant/issues/428) amended the protocol on its issue to authorize the follow-up that records a merged plan's decision ([D-0293](../decisions/journal/D-0293.jsonl)). The journal records a person's ratification; CI checks that record, and can't prove the person made it, as it can a comment on GitHub. Since #271's plumbing, the watcher takes it: a writer's retry of a plan's failed draft closes the draft and builds the plan again, in a pull request that replaces it ([D-0218](../decisions/journal/D-0218.jsonl)).
